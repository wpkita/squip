- type: feature | impact: low-medium | effort: medium
- resolution: Prompted by the user's question ("Are those even end to end or actually integration tests?"), corrected the misnomer. For consistency also renamed the just-introduced helper `E2eClient` → `ApiTestClient` and its env var `SQUIP_E2E_BASE_URL` → `SQUIP_API_BASE_URL` (neither used externally yet), and updated the squip-api/README testing section. Updated `Squip.sln`'s project entry. Verified: full solution builds clean (0 warnings/errors) after wiping stale bin/obj; `dotnet test --filter Category!=Integration` correctly excludes the integration dll and runs 6/6 unit tests green. (Historical `.refine/done.md` entries retain the old names, as they record past state.)

### Make E2E test base URL configurable instead of hardcoded

- type: feature | impact: low-medium | effort: medium
- resolution: All three tests in `Squip.EndToEndTests` (HabitsTests, HibitsTests, IdeasTests) hardcoded `new RestClient("https://localhost:8080/api")`, making them unrunnable against any non-local environment. Added a shared `E2eClient` static factory that reads the base URL from the `SQUIP_E2E_BASE_URL` environment variable (falling back to the `https://localhost:8080/api` default when unset/blank) and exposes `E2eClient.Create()`; replaced the three inline constructor calls with it. Documented the override in a new "Testing" section of squip-api/README.md. Verified the test project builds clean (0 warnings, 0 errors); the tests themselves require a live server so were not executed. Note surfaced while doing this (per the user's question): these are strictly black-box API/integration tests, not true end-to-end (they never exercise the squip-app frontend) — kept the existing `Squip.EndToEndTests`/`Category=End-to-end` naming to avoid a cross-cutting rename, but worded the README to describe them accurately as "black-box API tests."

### Migrate CI to GitHub Actions with a status badge (user request)

- type: bug | impact: high | effort: medium
- resolution: The repo is GitHub-hosted (github.com/wpkita/squip) but CI was Azure Pipelines, which requires an external Azure DevOps connection that clearly was not wired up — so CI was not actually running. Per the user's request, replaced it with native GitHub Actions: added `.github/workflows/ci.yml` triggering on push/PR to `main`, with least-privilege `permissions: contents: read` and two jobs on ubuntu-latest — `backend` (setup-dotnet via squip-api/global.json → `dotnet build` + filtered `dotnet test --no-build`) and `frontend` (setup-node 22 with npm cache → `npm ci` → `ng lint` → `ng build` → headless `ng test`). Deleted the now-redundant azure-pipelines.yml, added a CI status-badge chip to the top of the README, and rewrote the README CI section to describe the two workflow jobs. All step commands were already verified green on Linux in prior iterations (backend 6/6, frontend 25/25, lint clean, build OK). The badge shows live status once the workflow runs on the next push. Follow-up fix after the first run: setup-dotnet with `global-json-file` tried to download the literal pinned SDK `10.0.0` (a floor with rollForward:latestMinor, not a real downloadable build) and 404'd — switched to `dotnet-version: '10.0.x'` so CI installs the latest 10.0 feature band and global.json's roll-forward accepts it.

### Fix the failing frontend unit test suite (Angular 20 DI regressions)

- type: bug | impact: high | effort: medium
- resolution: Selected the "add frontend CI" item, but executing it revealed the squip-app Karma suite was entirely red — 16 of 25 tests failing — so per the maturity ladder (a red suite outranks every feature) the prerequisite was fixed first. Two root causes, both fallout from the Angular 15→20 upgrade where the specs were never updated: (1) 13 service/component specs never provided `HttpClient` (NG0201: No provider for HttpClient) — added `provideHttpClient()` + `provideHttpClientTesting()` to each TestBed; (2) AppComponent's spec injected the real Auth0 `AuthService` (NG0201: auth0.client token) and asserted a stale menu (Inbox/Outbox, 12 items) that no longer matches the template (5 nav pages) — mocked `AuthService`, replaced deprecated `RouterTestingModule` with `RouterModule.forRoot([])`, and rewrote the two DOM assertions against the current `appPages` (Angular 20 also dropped `ng-reflect-*` attributes, so the url check now asserts the nav config directly). Also added a `ChromeHeadlessCI` custom launcher (`--no-sandbox`) to karma.conf.js so the suite runs headless in CI/containers. Verified: `npm test -- --watch=false --browsers=ChromeHeadlessCI` → 25/25 pass; `ng build` still green.
